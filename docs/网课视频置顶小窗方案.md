# 网课视频置顶小窗方案（Windows / macOS）

> 目标：把浏览器里的网课视频，单独抽成一个跟随 QuizPane 主窗状态的置顶小窗。
> 要求：① 尽量只剩视频 + 进度条；② 与主窗 z-order / 老板键状态一致；③ 老板键隐藏时暂停、恢复时续播；④ 无明显性能开销。
>
> 本文结论先行：**Windows 架构不需要推翻，置顶问题当前代码已用 WinEvent 修掉。macOS 的“镜像不跟随自动播放”是 SCK 方案的架构级死结**——源窗只要对用户隐藏（挪出屏幕 / 被遮挡 / 最小化）就会被 Chrome 判定 occluded 而停止渲染，单屏下无解；因此 macOS 主方案建议从 SCK 镜像改为 Document Picture-in-Picture（Chrome 116+，让 Chrome 自己持有并渲染浮窗）。详见 §3.2。

---

## 0. 术语与现状速览

| 名词 | 含义 |
|---|---|
| **源窗 (source window)** | 扩展用 `chrome.windows.create({type:"popup"})` 拉出来的独立浏览器 popup，承载真正的 `<video>`。进入了 content-script 的“聚焦模式”，页面只剩播放器。 |
| **小窗 / 镜像 (replica)** | 用户最终看到的置顶窗口。macOS 上是一个 `NSPanel` + Metal 视图，内容由 ScreenCaptureKit 捕获源窗得到；Windows 上**就是源窗本身**（原生置顶）。 |
| **绑定令牌 (binding token)** | `__QUIZPANE_WINDOW_<uuid>__`。扩展把它写进 `document.title`，桌面端靠标题在系统窗口列表里定位源窗。 |
| **老板键 (boss key)** | 全局热键，隐藏/恢复 QuizPane 主窗，同时联动课程小窗。 |

现有两条后端路线（`external_window_types.hpp` 的 `BackendType`）：

- **Windows → `WindowsNativeTopmost`**：不做镜像，直接把浏览器 popup 源窗 `SetWindowPos(HWND_TOPMOST)` 顶起来，并用 WinEvent hook 持续复位 z-order。
- **macOS → 当前 `MacCapturedReplica`（建议改为 Document PiP）**：现状是 ScreenCaptureKit 捕获源窗 → Metal 渲染到置顶 `NSPanel`，源窗停到屏幕外 (`left:-10000`)。但该方案有架构级死结（§3.2），建议改为让 Chrome 自渲染的 Document PiP。

这两个选择本身是**平台特性倒逼的最优解**，下面解释为什么，以及每条路线各自的坑与修法。

---

## 1. 为什么两个平台必须用不同方案

核心矛盾：**“一个窗口稳定压在所有窗口最上面且永不抢焦点”这件事，Windows 做得到，macOS 做不到。**

### Windows：源窗直接置顶是可行的

Windows 的 `WS_EX_TOPMOST` 是**窗口级**属性，任何进程都能对任意 HWND 调 `SetWindowPos(HWND_TOPMOST, …, SWP_NOACTIVATE)` 把它顶起来且不抢焦点。所以最省事、性能最好、交互最完整（进度条能真点）的做法就是**直接顶源窗**，根本不需要镜像。这正是当前 `windows_window_topmost_backend.cpp` 做的。

### macOS：源窗置顶这条路是死的

macOS 没有跨进程的“把别人家的窗口设为置顶”的公开 API。窗口层级 (`window level`) 是**窗口所属进程**才能改的私有属性，你没法从 QuizPane 去把 Chrome 的某个窗口抬到 `NSFloatingWindowLevel`。可用的公开手段只有 Accessibility API 的 raise，但那是一次性的、会抢激活态，满足不了“持续压顶且不抢焦点”。

所以 macOS 只能退而求其次：**自己开一个属于 QuizPane 进程的 `NSPanel`（这个我们能随意设 level），把源窗的画面实时镜像进去。** 这就是 `MacCapturedReplica` 的由来——不是设计者想炫技，是被平台逼的。

> 你提到“用浏览器源窗：窗口无法一直置顶、会失去焦点”——这个现象在 **macOS 上是必然的**（无法跨进程置顶别人窗口），在 **Windows 上则是可以根治的**（见 §2）。所以“源窗直连”只在 Windows 成立。

## 2. Windows 路线：源窗原生置顶

### 2.1 现在怎么做的

`windows_window_topmost_backend.cpp`：

1. `EnumWindows` 按绑定令牌（写进标题）+ 校验进程是 `chrome.exe/msedge.exe/chromium.exe` 找到源窗 HWND。
2. `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE)` 置顶且不抢焦点。
3. **关键**：注册两个 `SetWinEventHook`（`EVENT_SYSTEM_FOREGROUND` 和 `EVENT_OBJECT_CREATE..LOCATIONCHANGE`），只要前台窗口变化或源窗自身 z-order 被 Chromium 改写，就 `enforceTopmost()` 复位。
4. 老板键隐藏 = `setVisible(false)` → `SW_HIDE`；恢复 = `SW_SHOWNOACTIVATE` + 重新顶起。

### 2.2 你踩的“无法一直置顶、会失焦”坑 —— 当前代码已修

看 git log，`79ae321 / 0c3cb9f / 4fd4df9` 这三个 commit 就是在解决这个：

- **为什么会掉置顶**：Chromium 自己会在处理焦点/显示变化时重写 popup 的 z-order，把你设的 TOPMOST 冲掉。一次性 `SetWindowPos` 顶不住。
- **修法**：用 WinEvent hook 事件驱动地**反复复位**（`handleWindowEvent` → `enforceTopmost`），而不是靠轮询。这个方向是正确的，性能也好（事件驱动，无空转）。

所以 Windows 的置顶问题**在 `feat_video_pane` 分支上已经解决**。如果你还在旧版本上看到失焦，先合并这几个 commit。

### 2.3 Windows 路线仍需注意的点

- **占用焦点问题的根源永远是 `SWP_NOACTIVATE` / `SW_SHOWNOACTIVATE`**——代码里已经全程带上了，保持即可。任何新增的 `ShowWindow`/`SetForegroundWindow` 都会破功。
- **老板键隐藏时暂停播放**：靠扩展侧 `command.boss_hide`（`content-script.js` 的 `pauseForBoss`），不是靠隐藏窗口。窗口 `SW_HIDE` 只是视觉隐藏。这条链路 OK。
- **性能**：源窗直连零拷贝、零捕获开销，是四条路线里最省的。WinEvent hook 是全系统事件回调，`handleWindowEvent` 里已经用 `pinned_/enforcing_` 早退，开销可忽略。
- **潜在增强（可选）**：目前只把 popup 顶起来，但 popup 仍带标题栏/地址栏残留。若要“尽量只剩视频”，Windows 侧靠的是 content-script 的聚焦模式（`enter_focus_mode` 把页面压成全屏纯视频），已经在做。真要更干净可以考虑给 popup 去边框，但会牺牲用户拖动，不建议。

**结论：Windows 路线保持现状，别改。**

## 3. macOS 路线：捕获镜像

### 3.1 现在的完整链路

```
扩展 create popup(源窗, focused:false, 屏幕内)
  → content: enter_focus_mode + ensure_playing   （先让它在屏幕内播起来）
  → 桌面端 attach: ScreenCaptureKit 捕获源窗 → Metal 渲染到 NSPanel
  → 首帧确认 (drawInMTKView 的 completedHandler) 才回 externalWindow.attached:success
  → 扩展收到 success，才把源窗 park 到 left:-10000（挪出屏幕但保持 normal，持续合成）
```

这里有几个设计决策是**对的、必须保留的**，注释里也写了原因：

- 源窗**不能最小化**，只能挪到屏幕外。因为最小化会让 Chromium 停止合成该窗口，ScreenCaptureKit 立刻停在最后一帧。
- 首帧确认后**才** park 源窗。若创建时就丢到屏幕外，SCK 还没锁定目标，Chromium 可能不提交首帧，镜像建不起来。
- 老板键恢复走 `prepareForRestore()` → 等一张**新帧**真正过了 Metal 呈现 → 才 `finalizeBossRestore`，避免恢复瞬间画面是旧的。

这套时序状态机（`_awaitingInitialPresentation` / `_awaitingRestorePresentation` / `_restoreEpoch` / 帧序号基线）设计得相当细致，说明作者很清楚 SCK 的坑。**不要推翻它。**

### 3.2 “镜像有时无法跟随源窗自动播放”—— 真根因（实测钉死）

> 本节结论来自真机实测（在 `mac_window_replica_backend.mm` 增设 `[QPD]` 诊断日志：每秒打印 SCK 收到的帧数、最新帧 PTS，以及用 `CGWindowList` 按 windowID 查的源窗实时 `frame` 与 `isOnScreen`）。**此前几版文档对根因的判断（"occlusion 被遮挡"、"源窗后台"、"park 出屏坐标"）经实测全部推翻或修正，本节为定论。**

#### 实测给出的铁证

让源窗经历"正常 → 被移出屏幕 → 恢复"，日志时间线如下（节选）：

```
行1-16  src_frame=(51,38 640x420) isOnScreen=true   delta≈30  ← 30fps 正常，源窗原地
行17-19 src_frame=(152,83 640x420) isOnScreen=true  delta≈29  ← 拖动源窗，仍正常
行20    src_frame=(14,870 113x47)  isOnScreen=true  delta=16  ← 源窗被推到屏幕底部边缘、缩小，帧率开始掉
行21    src_frame=(0,0 0x0)         isOnScreen=false delta=0   ← 源窗彻底消失(0x0)，立刻 0 帧卡死
```

#### 真根因：源窗 `isOnScreen=false` 即死

**决定 SCK 能否拿到帧的，是源窗在窗口服务器层面的 `CGWindowIsOnscreen` 标志——只要它为 `true`（源窗在某个屏幕的可见矩形内），SCK 就持续 30fps 出帧；一旦变 `false`（源窗被移出屏幕 / 最小化 / 隐藏成 0x0），SCK 立刻 0 帧卡死。**

这推翻了此前几个错误判断：

| 此前假设 | 实测 | 结论 |
|---|---|---|
| “park 出屏 `left:-10000` 是死因” | 死时 frame 是 `0x0` 而非 `-10000,38` | 不准确——死因是"移出屏幕"这个动作的结果，不是某个坐标值 |
| “源窗后台（Edge 非前台）即死” | 屏内被盖、Edge 后台时仍 30fps 正常 | **错**——非前台不死 |
| “被遮挡即死” | 屏内被盖住（也算遮挡）时正常 | **错**——`CGWindowIsOnscreen` 仍 true |

#### 关键认知：两个不同层的"可见"标志

这澄清了前几轮最大的混乱。macOS 上有两个**不同层**的可见性标志，别混为一谈：

| 标志 | 层 | 含义 | 谁消费 |
|---|---|---|---|
| `CGWindowIsOnscreen`（本节日志打的） | 窗口服务器 / CoreGraphics | 窗口的矩形是否落在某块屏幕的可见区域内 | **ScreenCaptureKit** —— 它决定 SCK 给不给帧 |
| `NSWindowOcclusionState` | AppKit | 窗口是否被其它窗口完全遮挡 | **Chrome** 节流逻辑吃它（停合成/节流 rAF） |

实测证明：**SCK 的帧投递只看 `CGWindowIsOnscreen`**，不看 Chrome 的 occlusionState。所以"源窗被别的窗口完全盖住、但仍在屏幕可见矩形内"时，`CGWindowIsOnscreen=true`，**SCK 照常 30fps**——哪怕 Chrome 的 occlusionState 可能已 false。这一点前几轮反复纠结的"被遮挡会不会死"，实测给出答案：**SCK 这条路，被遮挡不死，只有移出屏幕才死。**

> 注意：这没有完全否定 Chrome 的 occlusion 节流存在；它说明的是 **SCK 的帧投递不依赖它**。源窗在屏内被盖住时，即使 Chrome 在 occlusion 层面想节流，SCK 仍能从窗口服务器的合成层拿到帧。这是实测坐实的事实，不是文档推断。

#### 因此 SCK 方案完全可用，且极简单

真根因锁定后，结论简单得令人意外：

**只要源窗保持在屏幕可见矩形内（`CGWindowIsOnscreen=true`），SCK 镜像就 30fps 稳定。** 不需要源窗在前台、不需要不被遮挡、不需要虚拟显示器、不需要屏幕录制权限以外的任何特殊手段。

当前代码之所以卡，元凶就是 service-worker `handleExternalWindowAttached` 里那句 `chrome.windows.update(courseWindowId, {state:"normal", left:-10000, ...})`——首帧确认后把源窗 park 出屏，源窗立刻 `isOnScreen=false`，镜像随之死。**删掉这个 park（源窗留在创建时的屏内位置），镜像即活。**

#### 隐蔽方案：如何让源窗"留屏内可见"又不碍眼

删 park 后，源窗会正常显示在屏幕上，与镜像 panel 并存——这违背"小窗独立出来、用户不该看见源窗"的初衷。几条隐蔽思路，按实测置信度排序：

| 隐蔽方案 | 实测置信度 | 说明 |
|---|---|---|
| **源窗留屏内、被别的窗口完全盖住** | ⚠️ 待实测（最可能可行） | 实测证明 SCK 只看 `CGWindowIsOnscreen`，被盖住时该标志仍 true、SCK 正常出帧。若"被完全盖住"也能维持 `CGWindowIsOnscreen=true`，则这是最隐蔽可行的落点——源窗在屏内、被 QuizPane 主窗或镜像 panel 整个压住，用户看不见但 SCK 照拿帧。**这条前几轮没测清，落实施前需一组对照实测确认。** |
| 源窗留屏内、缩到角落 + content-script 聚焦模式压成纯视频 | ✅ 实测可行（行17-19 即此形态） | 源窗可见但不抢镜，占屏角落。代价是占屏幕一块区域，丑但稳。保底方案。 |
| 源窗缩成 1px 几乎不可见 | ❌ 实测反证 | 行20 显示 113x47 就开始掉帧，1px 极可能触发 `isOnScreen=false` 而死。赌不赢。 |
| 源窗塞到全屏应用的 Space 下面 | ❌ 高风险 | macOS 全屏窗口独占 Space、z-order 极特殊，极易把源窗判 `isOnScreen=false`。不建议。 |
| 源窗挪到副屏可见处 | ✅ 可行但受限 | 依赖多屏硬件，非通解。 |

**最该补的一组实测**：源窗留在屏内、尺寸正常，但被 QuizPane 主窗**完全盖住**（不留任何露出像素），观察 `[QPD] frame stream` 是否仍 30fps。若仍正常 → "被完全盖住"即最优隐蔽落点，源窗对用户隐形、SCK 照常出帧，A 方案既稳又干净。若变 0 帧 → 退回"角落可见"保底形态。

#### 附带的次因：`ensure_playing` 与 attach 的时序竞态

`enterCourseWindow` 里是 `await ensure_playing()` **然后** `attachExternalWindow()`。但 `ensure_playing` 里 `play()` 之后只等了 120ms 就返回，某些课程站点的播放器会在稍后被自己的脚本二次暂停（防挂机），此时镜像已建好却停在暂停画面。

**修法**：attach 成功后**再补一次 `ensure_playing`**，并把 content-script 里对“被站点重新暂停”的检测加进 `reportStatus` 心跳（现在心跳只在 playing 时每秒发，暂停后就沉默了——桌面端无从知道它被偷偷停了）。

### 3.3 macOS 交互（进度条可点）现状

> 说明：本节描述的是**现有 SCK 镜像方案**下的交互实现。若按 §3.2 切换到 Document PiP，这套坐标换算逻辑将不再需要——PiP 里搬的是原生播放器 DOM，进度条直接可点。以下留作镜像方案的记录与降级兜底参考。

镜像是一张画面，本身不可交互。当前用 `handleMirrorPointer` 把镜像上的点击/拖拽换算成归一化位置，通过 `videoControlRequested` → `command.video_control` 回传给 content-script 去 `seek`/`toggle`。底部 56px 判定为进度条区。**这套是可用的**，但要注意：

- 它依赖 content-script 能拿到 `video.duration`，直播或未加载完会失效（代码已处理返回 error）。
- 精度受镜像缩放影响。够用，但不如原生控件精确——这是镜像方案的固有代价。

## 4. 老板键联动：两个平台的状态机

老板键要满足的三件事映射到实现：

| 需求 | Windows | macOS |
|---|---|---|
| **隐藏后小窗消失** | `setVisible(false)` → `SW_HIDE` 源窗 | `NSPanel orderOut` |
| **恢复后小窗回到最顶** | `SW_SHOWNOACTIVATE` + `enforceTopmost` | `activateMirrorPanel`（`NSApp activate` + `makeKeyAndOrderFront`） |
| **隐藏时暂停 / 恢复时续播** | 扩展 `pauseForBoss` / `restoreFromBoss` | 同左（平台无关，都走扩展） |

关键编排在 `browser_bridge.cpp::requestBossHide/requestBossRestore`：

- **隐藏**：先 `externalWindowManager_->setVisible(false)`（立即视觉隐藏），再 `command.boss_hide`（扩展暂停视频）。顺序对——视觉优先，播放状态异步跟上。
- **恢复（SCK 镜像方案下的两段式）**：`prepareForRestore()` 记录帧基线并 orderOut → `command.boss_restore` 让扩展恢复源窗 normal + `video.play()` → 等**新帧**过 Metal 呈现（`restoreFrameReady`）→ 且命令回执到（`bossRestoreCommandCompleted_`）→ 才 `finalize_boss_restore`。这保证“恢复出来的第一眼就是动的新画面”，不是旧帧。设计正确。
- 主窗触发点 `main_window.cpp::toggleWindowVisibility`：`hide()` 前先 `requestBossHide()`，`show()` 后 `requestBossRestore()`，并且有 150ms 去抖。OK。

**桌面端编排顺序与去抖不用动。** 若 macOS 切换到 Document PiP，恢复链路会简化：不再需要“等新帧过 Metal 呈现”那套两段式确认（PiP 由 Chrome 自渲染，`play()` 后画面立即动），`requestBossRestore` 的 macOS 分支可直接改为“重新 `requestWindow()` 搬回节点 + `play()`”。无论走哪条方案，都建议在恢复完成后补一次 `ensure_playing`，防止源窗被站点脚本二次暂停。

## 5. 性能开销评估

| 路线 | 主要开销 | 评价 |
|---|---|---|
| Windows 原生置顶 | 一个全系统 WinEvent 回调（早退快）、偶发 `SetWindowPos` | 极低，几乎零 |
| macOS Document PiP（建议主方案） | Chrome 自渲染浮窗，无捕获、无 Metal、无屏幕录制权限 | 低，远优于镜像 |
| macOS SCK 捕获镜像（现状/降级） | SCK 捕获（GPU 编码）+ Metal 渲染，30fps | 中等。已用 `minimumFrameInterval` 限帧、`queueDepth=3`、按需 `draw`，隐藏时 orderOut 停渲染。可接受 |

若暂时保留 SCK 镜像，进一步降耗的空间（可选）：

- 视频暂停时（收到 content 的 paused 心跳）把 `_metalView.preferredFramesPerSecond` 降到 1 或直接 `paused=YES`，画面本来不动，没必要 30fps 空转。**这是最值得做的一个优化**，直接砍掉暂停时的持续 GPU 开销。
- 小窗被 QuizPane 主窗完全遮挡时同理降帧。

## 6. 最终建议：改哪、不改哪

### 保持不动（架构正确）
- Windows 的双后端策略与原生置顶（`WindowsNativeTopmost`）——平台特性决定，无更优解。
- Windows 的 WinEvent 置顶复位机制——已修好失焦/掉顶。
- 老板键的桌面端编排顺序与去抖。

### macOS 主方案：从 SCK 镜像切换为 Document PiP（需原型验证）
1. **【核心结论】** SCK 镜像在单屏下存在架构级死结：源窗只要对用户隐藏就会被 Chrome 判定 occluded 而停渲染，`MAC_SOURCE_PARK_*` 调参无法解决。
2. **【建议主方案】** 改用 Document Picture-in-Picture（Chrome 116+）：把真实播放器 DOM 搬进 Chrome 自渲染的浮窗，进度条原生可点、无捕获开销、无死结。
3. **【落地前置】** 先做最小原型，验证三个代价点：目标站点是否禁 PiP、PiP 窗与 QuizPane 置顶 panel 的 z-order 能否与老板键严格同步、搬 DOM 是否导致播放器错乱。
4. **【降级】** 验证不通过则退回 SCK 镜像并接受多屏限制；视频 PiP（现有 `pipButton`）保留为最末兜底。

### 无论走哪条方案都建议修
5. **【次因】** attach 完成后与老板键恢复完成后各补一次 `ensure_playing`，防站点脚本二次暂停。
6. **【心跳】** content-script 心跳在“被动暂停”时也上报一次（现在暂停即沉默），让桌面端能感知源窗被偷停。

### 若暂时保留 SCK 镜像
7. **【优化】** 镜像在源窗暂停/被完全遮挡时降到 1fps 或 `paused=YES`，砍掉空转 GPU 开销。

### 不建议做
- 不建议 macOS 用“把源窗挪出屏幕 / 压在主窗下被遮挡”来藏源窗——前者是当前 bug 的成因，后者既拖动露馅又同样触发停渲染。
- 不建议 Windows 走镜像：白白增加捕获开销，还丢了进度条原生可点。

---

## 7. 一句话总结

Windows 路线是对的，置顶坑已用 WinEvent 修好，别动。macOS 的“镜像不跟随播放”不是调参 bug 而是 SCK 方案的死结——**源窗只要对用户隐藏就会被 Chrome 判定 occluded 而停渲染，单屏下没有“既隐藏又还在渲染”的落点**。正解是让 Chrome 自己持有并渲染浮窗，即改用 Document Picture-in-Picture；落地前先用最小原型验证站点兼容性、z-order 同步、搬 DOM 三个代价点。

> 把各分册的建议按**优先级**和**类型**汇总成一张可执行清单，供排期参考。

## 一、全项目共性问题

本项目工程质量整体高（spec 文档完备、注释讲"为什么"、已有多处针对性性能优化）。
主要的技术债集中在**两个巨型 UI 控制器类**：

| 文件 | 行数 | 问题 |
|---|---|---|
| `apps/desktop-qt/src/ui/main_window.cpp` | 2987 | 单类承担做题/目录/解析/更新/热键/外观/课程陪伴 |
| `apps/bank-studio/src/studio_window.cpp` | 3112 | 单类承担四步向导 + 复核编辑器全部逻辑 |

这两个类是重构的**最高优先级**，也是新人最难上手的地方。核心思路一致：
**把"页面/步骤"拆成独立控制器，主窗口退化为装配器 + 页面切换。**

## 三、可读性优化（跨模块通则）

本项目已有很好的注释文化（`CONTRIBUTING.md` 要求注释讲"约束、边界和为什么"，禁止跨技术栈类比）。
巩固方向：

1. **巨型函数拆分**：`request()`、`packageProvider()`、各种回包处理函数普遍偏长，一行多语句密度高。
   拆成命名小函数是收益最直接的可读性改进，且顺带方便单测。
2. **显式状态优于隐式**：`ActionMode`、`external_window::State` 这类显式枚举状态机是好实践，
   建议把"当前页面"等隐式依赖 `QStackedWidget` currentIndex 的状态也提升为枚举。
3. **接口镜像命名**：manager 与后端、UI 侧与题库侧的对称方法名（如 `attach`/`request`）
   降低跨层跳转成本，保持。
4. **spec 同步是硬约束**：改动 `spec/01~06` 覆盖的行为时，必须同步 spec（`quizpane-spec-sync` 技能）。
   本目录 `spec/refactor/` 是架构视角补充，改架构/拆类后也应回来更新对应分册的代码位置。

## 四、性能优化（已验证模式，推广而非重造）

项目已经做过多处**针对 Win7 x86 低配**的优化，这些是应当在新功能里**复用的范式**：

| 已验证模式 | 出处 | 推广到 |
|---|---|---|
| O(题+类) 一次遍历累计，避免 O(题×类) | `catalog.list`（`declarative_provider.cpp:373`） | 任何"逐分类统计全量"的场景 |
| 预算索引表（load 时算一次） | `questionCountByCatalog_` | 高频查询的聚合值 |
| 图片懒加载 + 翻页释放旧图 | 结果长图、PDF 页图 | 任何大图展示 |
| `QSaveFile` 原子写 | `DraftStore::save` | 任何本地文件持久化 |
| 异步回包代号过滤 | `ProviderLoader::generation_` | 任何可切换资源的异步回调 |

**慎动区**：规则引擎的确定性（同输入同输出）和 C ABI 契约（`struct_size`/版本协商）是系统的
稳定基石，优化时不得破坏这两个不变量。

## 五、建议的推进顺序

1. **先做 #7、#12、#14、#16**（低风险，加测试/补文档/明确边界），建立安全网。
2. **再做 #3、#5、#9、#13**（题库侧局部重构 + 性能，有测试覆盖，风险可控）。
3. **最后做 #1、#2、#4**（两个巨型 UI 类的拆分，改动面大，需分阶段小步提交 + 手动验证做题/制作全流程）。
4. 每步都跑 `ctest --preset dev`（或 Release 的 `ctest --preset release`），UI 大改需实机验证。

## 六、项目/模块结构优化（组织层面的可读性）

前面各节的"可读性"聚焦**代码内部**（函数拆分、命名、显式状态、注释）。
但仓库**目录/模块的组织**同样影响可读性与新人上手成本，且当前存在明显冗余。
以下建议不改代码行为，只做归位；纯文档/物料的移动风险低，但需 `git mv` 保留历史。

### 6.1 顶层目录语义重叠，需归并

历史上按需新增目录，导致**同义目录并存、单文件成目录**，顶层一眼看去分不清职责：

| 现状目录 | 内容 | 建议 |
|---|---|---|
| `docs/`（技术文档主目录，~40 文件） | 技术方案、调研、release-notes | 作为**唯一**技术文档目录保留 |
| `doc/`（3 文件） | 回归报告、代码评审、规则审查 | 并入 `docs/` —— 与 `docs` 并存纯属命名事故 |
| `material/`（1 文件） | 单篇 MinerU 调研 | 并入 `docs/` —— 单文件不足以成目录 |
| `marketing/`（~30 文件） | 小红书推广 | 作为**唯一**营销物料目录保留 |
| `market/`（~11 文件） | 推广文案 + images | 并入 `marketing/`（如 `marketing/copy/`） |
| `advertise/`（~11 文件） | 小红书文案/合规/冒烟记录 | 并入 `marketing/` —— 三者语义同为"推广"，小红书内容现散在三处 |

归并原则：**技术文档统一 `docs/`，营销物料统一 `marketing/`**；`doc`、`material`、`market`、
`advertise` 四个目录消化后删除，顶层由 6 个文档/物料相关目录收敛到 2 个。

### 6.2 构建产物不应入库

`dist/` 内含 `quizpane-course-companion` 与 `quizpane-course-companion 2`（带空格的重复副本）、
`*.zip`、按 commit 命名的 `win7-ready-dfc2b71/` 等，明显是**本地构建/打包产物**。
建议：产物目录（`dist/`、`build/`、`cmake-build-*/`、`tmp/` 等）统一纳入 `.gitignore`，
已入库的先 `git rm --cached` 移出版本库，避免仓库体积膨胀与"哪个才是最新"的混淆。

### 6.3 两个 app 的源码组织粒度对齐

| app | 现状 | 建议 |
|---|---|---|
| `apps/desktop-qt/src/` | 已分层：`ui/` `platform/` `external_window/` `browser/` | 作为对齐范式 |
| `apps/bank-studio/src/` | 十余个文件**平铺**在 `src/` 根下 | 按职责建子目录（如 `ui/` `review/` `source/`），与 desktop-qt 对齐 |

此项与 #2（`StudioWindow` 拆分）天然协同：拆出复核编辑器等组件时，顺势落到新子目录，
避免"拆了类却仍堆在一个目录"。

### 6.4 优先级与排期

均为**低优先级、低风险**，建议并入第五节第 1 步"建立安全网"阶段一起做：
纯物料/文档移动（6.1、6.2）可独立小 PR 完成；6.3 建议与 #2 合并推进，减少一次目录搬迁。

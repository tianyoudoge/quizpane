## 一、功能定位与"两条链路"的真正含义

制作端把原始资料（txt/docx/pdf + 可选答案册）变成可安装的 `.quizpane-provider` 题库包。
它有两条**提取**链路，但**只有一个解析引擎**：

| | 链路 A · 规则识别 | 链路 B · 智能识别（MinerU） |
|---|---|---|
| 本质 | 提取后端 = 本地 `DocumentExtractor` | 提取后端 = 云端 `MinerU` 服务 |
| 运行 | 纯本地、离线 | 本地只是 HTTP 客户端 |
| 产物 | `ExtractedDocument` | 同一个 `ExtractedDocument`（经 `MinerUOutputAdapter` 适配） |
| 之后 | **共用**同一个 `RuleBasedBankGenerator` 切题 | 同左 |

**核心认知（写代码前必读，来自 `spec/01` §4）**：
"智能识别" **不是**"让模型理解题目"，而是"用 MinerU 的版面分析能力把 PDF 变成带坐标的文本"。
提取之后，两条链路都走**同一个确定性规则引擎**切题。因此：

- MinerU 是**提取后端，不是 fallback**——不存在"规则失败后偷偷调模型"的混合路径。
- MinerU 提取失败 → 该文件 `Failed`，**不降级**到规则或模型。

## 二、四步向导与数据流（对照复杂版图）

`StudioWindow`（`apps/bank-studio/src/studio_window.cpp`，3112 行）是四步向导：

```
01 选择资料 → 02 自动整理 → 03 检查问题 → 04 完成打包
```

1. **① 选择资料**：每行 `SourceRowWidget` = 文件 + 答案策略（自动检测/含答案/无答案）+ 答案文件配对。
   状态 `sourcePaths_` / `answerPolicyByQuestion_`（Auto 默认，人工选择只作覆盖）。
   可为 PDF 指定 MinerU ZIP 走云端提取。

2. **② 自动整理**：`GenerationWorkflow`（`generation_workflow.cpp`）对每个
   `SourceMaterialGroup` 执行「提取 → 解析」，在 `QtConcurrent` 工作线程跑，进度信号驱动 UI。
   - 提取：本地 `ExtractorRegistry` 或 MinerU 云 ZIP → 统一 `ExtractedDocument`。
   - 解析：`RuleBasedBankGenerator::generate` → `ReviewResult`。

3. **③ 检查问题**：`QTreeWidget`（材料分组 + 独立题，复选框=收录开关）+ 右侧详情编辑器 +
   `CropDialog` 图片重裁。用户编辑**原地改 `QJsonObject`**，不产生新 id；**原 PDF 永不修改**。

4. **④ 完成打包**：`packageProvider()` 组 `bank.json` → `validateBank`（C++ 校验器权威）→
   `manifest.json` → ZIP → 三重自检 → `ProviderInstaller` 安装 → `RunningAppHandoff` 交刷题端。

## 三、两个统一产物（下游只认它们）

- **`ExtractedDocument`**（`document_extractor.hpp`）：两条提取链路的共同产物。含纯文本、
  版面锚点（`questionAnchors`/`optionLabelAnchors`/`lineAnchors`）、按需页面 PNG、
  `extractionBackend`（空/`local-qt` 本地，`mineru-*` 云端）。规则引擎**只用** backend 标志启用
  "经云端坐标验证"的能力，**不解析 MinerU 原始 JSON**。
- **`ReviewResult`**（`review_result.hpp`）：规则与模型路径都输出它。关键分区：
  `questions`（ok+soft，默认勾选）/ `needsReviewQuestions`（hard，**禁止猜测答案**）/
  `materials` / `assets`（正式附件，进包）/ `reviewAssets`（校对裁图，**不进包**）/
  `hasAnswerKey`（整库二选一，不允许混合）。

## 四、设计约束（改代码前必读，摘自 `spec/01` §5）

1. 规则引擎是**纯函数**：同输入同输出，不依赖网络/窗口/时间。
2. **宁缺毋滥**：识别不出答案的题进 `needsReviewQuestions` 人工复核，禁止用猜答案换 Schema 表面合法。
3. 归一化用 **NFC 不用 NFKC**（NFKC 会把圈码 ① 分解成裸 1，丢失选项标记）。
4. 来源只记文件名/页码/归一化坐标，**不含本机绝对路径**。
5. 校对图（`reviewAssets`）**不进安装包**，只有 `assets` 打包。
6. 编辑不产生新 id；`id` 格式 `r<文档序>-q<原始题号>-<全局递增>`。
7. `hasAnswerKey` 整批一致；Auto 先按含答案探测，无答案证据才重跑为无答案库。

## 五、重构建议

1. **【高】`StudioWindow` 3112 行同样偏重**，与 `MainWindow` 是同一类问题。建议把
   "第三步复核编辑器"抽成独立组件（树的构建、详情面板、CropDialog 联动自成一体），
   `StudioWindow` 只管四步切换与 workflow 调度。

2. **【中】提取后端注册表化**。目前本地/MinerU 两条路在 workflow 内分支。若未来要接更多
   提取后端（如其它云服务），可把 backend 抽象成 `IExtractor` 接口 + 注册表，
   workflow 只面向接口，`extractionBackend` 字段驱动能力开关的逻辑集中到一处。

3. **【中】`bank_validator.cpp` 与 JSON Schema 的漂移**。当前运行时以 C++ 校验器为准，
   Schema 文件滞后（`spec/01` §3.3 明确标注 `$defs.asset` 只放行 `path/alt` 是过时的）。
   建议：要么从 C++ 校验器生成 Schema，要么加一个测试断言两者一致，避免第三方按 Schema
   写插件时踩坑。

## 六、性能建议

- **【已做，可借鉴】页面图片懒加载**：扫描页立即保留 PNG，文字页 `ensurePdfPageImages` 按需渲染
  （`spec/01` §3.1）。新增依赖页面图的功能时应沿用懒加载而非一次性全渲染。
- **【已做】`catalog.list` 掌握度 O(题+类)**：题库侧已把"逐分类遍历全量题"优化为一次遍历累计
  （`declarative_provider.cpp:373` 注释）。制作端若有类似"逐分类统计"的 UI，应对齐这个模式。
- **【中】大 PDF 提取的内存峰值**：`spec/06` 已针对 Win7 x86 做过 preview 内存收敛。
  新增批量提取时注意工作线程里不要同时持有所有页 PNG。

## 七、可读性建议

- 这块的 spec 文档质量是全项目标杆（每条结论带 `file:line`）。改动这两条链路时，
  **务必同步 `spec/02~05`**，这是 `quizpane-spec-sync` 技能的硬要求。
- `ReviewResult` 的字段语义微妙（`assets` vs `reviewAssets`、`questions` vs `needsReviewQuestions`），
  已有良好注释，保持；新增字段时同步在 `review_result.hpp` 注释里写清"是否进包/是否可猜"。

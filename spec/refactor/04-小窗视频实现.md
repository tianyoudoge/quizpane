# 04 · 小窗视频实现导读（macOS / Windows）

> 覆盖刷题端的"网页课程小窗"能力：把浏览器里的课程视频窗口置顶/镜像到刷题小窗旁。配套图：
> [小窗视频简单版](assets/dataflow-video-simple.svg) · [小窗视频复杂版](assets/dataflow-video-complex.svg)。
>
> 关键目录：`apps/desktop-qt/src/external_window/`（窗口后端）与 `apps/desktop-qt/src/browser/`（浏览器桥）。

## 一、功能定位

场景：用户一边看网页课程视频、一边用 QuizPane 刷题。小窗视频功能让课程视频窗口能稳定显示在
最前，并把播放状态同步给刷题端（甚至从刷题端控制播放）。触发数据来自浏览器扩展。

这块的核心难点是**跨平台窗口操作**——不同操作系统"让别人的窗口置顶/镜像"的能力天差地别。
项目用 `ExternalWindowManager` 一个统一入口，把平台差异封装在后端里。

## 二、统一入口 + PIMPL：一套接口四种后端

`ExternalWindowManager`（`external_window_manager.hpp`）是对外唯一入口，做题窗口只认它，
不关心当前跑在哪个平台。跨平台差异用 **PIMPL 惯用法**（`class Private;` + `Private* d_`）+
编译期 `#if` 隔离——好处是这个头文件**不用 `#include windows.h / AppKit.h`** 等平台专属头
（`external_window_manager.hpp:9-13`）。

对外接口很小：`attach(request)` / `detach()` / `setVisible()` / `prepareForRestore()` /
`requestScreenCapturePermission()` / `state()`，加几个信号
（`attachFinished` / `stateChanged` / `restoreFrameReady` / `videoControlRequested`）。

后端类型（`external_window_types.hpp:12`）：
- `WindowsNativeTopmost`（Windows，已启用）
- `MacCapturedReplica`（macOS，已启用）
- `LinuxX11NativeTopmost` / `LinuxWaylandPortalReplica`（预留，未启用）

会话状态机（`external_window_types.hpp:23`）单向流转：
`Idle → ResolvingTarget → (Attached/Starting) → Active`；源窗口暂丢 → `Recovering` 自动重连；
`Failed`/`Stopped` 终态。

## 三、两平台策略的根本差异

| | macOS · MacCapturedReplica | Windows · WindowsNativeTopmost |
|---|---|---|
| 策略 | **捕获画面 + 镜像渲染** | **直接置顶原生窗口** |
| 实现 | ScreenCaptureKit 捕获源窗口 → 渲染到自己的置顶窗口 | `SetWindowPos(HWND_TOPMOST)` 抬 z-order |
| 是否复制画面 | 是（镜像帧） | 否 |
| 权限 | 需"屏幕录制"权限 | 无需特殊权限 |
| 交互 | 可交互：手势转发回浏览器控制播放 | 直接操作原生窗口 |
| 源窗口最小化 | 仍能镜像最后帧 | 无内容可见（局限） |
| 代码语言 | Objective-C++（`.mm`） | C++ + Win32（`.cpp`） |

### macOS 侧要点（`mac_window_replica_*.mm`）

- **定位源窗口**：`CGWindowListCopyWindowInfo` 按 `windowId` 找源窗口（`capture.mm:54`）。
- **捕获**：`SCStream` + `SCStreamConfiguration`，注意 `SCWindow.frame` 是逻辑点、配置需实际像素，
  有一次坐标换算（`capture.mm:239`）。
- **权限判定**：**不信** `CGPreflightScreenCaptureAccess` 旧预检（授权后它仍可能短暂返回 false），
  真正发起 `ScreenCaptureKit` 请求才是权限结论（`capture.mm:138`）。
- **异步生命周期**：SCStream 建立、首帧确认等回调可能在用户已 `detach` 之后到达，回调里要校验
  会话仍有效（`capture.mm:130`）。
- **恢复防黑屏**：`restoreFrameReady` 让老板键恢复时等一帧就绪再显示。

### Windows 侧要点（`windows_window_topmost_backend.cpp`）

- **定位**：`EnumWindows` + `findWindowCallback` 按标题/类名匹配 Chromium popup。
- **重试**：Chromium 创建 popup 与把 `document.title` 同步到原生窗口标题之间有延迟，第一次
  `EnumWindows` 可能找不到。`ExternalWindowManager::tryAttachWindows` 手写 **50ms 轮询、2s 超时**
  的重试（`external_window_manager.cpp:143-183`）。这是 Windows 没有 macOS 那种内建重试机制的补偿。
- **置顶校验**：`WS_EX_TOPMOST` 只表示"属于置顶带"，不代表真在最前；用
  `GetWindow(window, GW_HWNDPREV)` 重走实时 z-order 才是准的（`:181-187`）。
- **监听**：`SetWinEventHook` 监前台/对象事件，目标丢失时记 `windows-topmost-target-lost`。

## 四、触发链路：浏览器扩展 → 桥 → 管理器

（见复杂版图第①段）

1. **浏览器扩展** 检测 HTML5 播放器，上报窗口 id / 播放状态。
2. **`BrowserBridge`**（`browser_bridge.hpp`）：WebSocket 服务，**仅监听 IPv4 loopback**、
   `kBridgePort=38427`、消息 16KB 上限。端口刻意避开 Windows 默认动态端口范围
   `49152-65535`，防止 Hyper-V 保留端口导致 `listen()` 返回“地址受保护”。协议**只传播放器状态与白名单控制命令**，
   **不承载网页内容、Cookie 或视频地址**（`browser_protocol.hpp:11`）——网络边界很克制。
   `parseMessage` 独立成模块，便于不启 WebSocket 就单测协议。
3. **`MainWindow::updateCourseCompanion`** 更新课程陪伴页 / 视频状态条。
4. **`ExternalWindowManager::attach(AttachRequest)`**（含 `chromeWindowId`/`bounds`/`preferredFps`）
   驱动对应平台后端。

反向控制：镜像窗口的手势（macOS）→ `videoControlRequested` 信号 → 桥转发回扩展控制播放。

### Win11 真实站点验收（2026-09-21）

在已启用 Hyper-V 的 Windows 11 x64 上，修复后桥接可成功监听 `38427`，扩展显示“已连接本机
QuizPane”。B 站 `BV1jeUbBYELu` 经首次站点授权后可绑定，并由 Edge 移入独立的原生视频
聚焦小窗；实际讲课视频持续播放，浏览器媒体控制可暂停与恢复。该验证使用 Win7 x64 绿色包，
确认修复不依赖仅现代系统才有的部署组件。远程桌面无法可靠注入全局 `Ctrl+H`，老板键实体键盘
路径保持待本机复验。

## 五、重构建议

1. **【中】Linux 后端补齐或明确声明未支持**。`BackendType` 已预留两种 Linux 策略但未实现，
   `attach` 在非 mac/win 平台直接返回 `Unsupported`（`external_window_manager.cpp:90-98`）。
   建议在文档/代码注释里明确"Linux 小窗视频暂不支持"，避免使用者误判。

2. **【中】重试逻辑归位**。Windows 的 50ms 轮询重试写在 `ExternalWindowManager`（平台无关层），
   而 macOS 的重试在后端内部。策略不对称。建议把"attach 重试"抽象成两个后端都实现的能力，
   或统一由 manager 编排，让平台无关层不出现 `#if Q_OS_WIN` 的重试细节。

3. **【低】`AttachResult`/`Capabilities` 已建模良好**，可作为其它跨平台能力（如全局热键）的
   建模参考——用显式 `errorCode` 枚举 + 人类可读 `error` 字符串，而非布尔 + 魔法字符串。

## 六、性能建议

- **【中】`preferredFps`（默认 30）** 是捕获镜像的主要开销来源（仅 macOS）。刷题场景视频多为
  讲课画面，可考虑在窗口不可见 / 老板键隐藏时降帧或暂停捕获，减少 CPU/GPU 占用与耗电。
- **【中】镜像帧的内存/拷贝**：确认 `renderer.mm` 是否每帧都做全尺寸拷贝。可复用帧缓冲、
  按目标小窗尺寸缩放后再持有，避免持有全分辨率帧。
- **【低】Windows 纯置顶几乎无额外开销**，主要成本是 `SetWinEventHook` 回调频率，保持现状即可。

## 七、可读性建议

- `external_window_types.hpp` 的枚举注释（四种后端策略、状态机流转）是理解这块的最佳入口，保持。
- macOS 的 `.mm` 文件混了 Objective-C 与 C++，对纯 C++/服务端背景的人门槛最高。建议在每个
  `.mm` 文件头补一句"本文件负责捕获/渲染/输入的哪一段"，`capture.mm` 已有较多"为什么"注释可参考。
- 平台后端的公有方法命名已与 `ExternalWindowManager` 对齐（`attach`/`detach`/`setVisible`），
  保持这种"接口镜像"命名，读者能快速在 manager 与后端间对应。

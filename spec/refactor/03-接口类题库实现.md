# 03 · 接口类题库实现导读（C ABI 插件框架）

> 覆盖 `sdk/` 的题库插件框架与内置声明式题库。配套图：
> [接口题库简单版](assets/dataflow-provider-simple.svg) · [接口题库复杂版](assets/dataflow-provider-complex.svg)。
>
> 关键文件：`sdk/include/quizpane/provider_abi.h`、`sdk/include/quizpane/provider_loader.hpp`、
> `sdk/src/declarative_provider.cpp`、`providers/demo/demo_provider.cpp`。

## 一、功能定位

"接口类题库"指的是：题库以**插件**形式接入宿主，而不是把所有题库类型硬编码进刷题端。
QuizPane 用一套 **C ABI + JSON-RPC** 定义 Host（刷题端）与 Provider（题库）之间的契约。
这套设计可以类比"桌面进程内的一套小型 HTTP/RPC 协议"：**函数指针是 endpoint，JSON 是请求/响应 DTO**
（`provider_abi.h:21-28` 的注释原话）。

有两类 Provider：
1. **内置 `DeclarativeProvider`**：由 `bank.json` 直接驱动，制作端产出的题库都走它。
2. **第三方动态库**（如 `providers/demo`）：独立编译的 `.dll`/`.so`，可去远端 HTTP 抓题。

## 二、为什么是 C ABI 而不是 C++ 虚函数接口？

这是本模块最值得理解的设计决策（`provider_abi.h:21-28`）：

> C++ ABI 会随编译器、标准库和编译选项变化，MSVC/Clang/GCC 之间尤其不能直接互通。
> 采用 C ABI + UTF-8 JSON，Host 与 Provider 就可以**独立编译**，只要 ABI 版本一致即可组合。

对服务端工程师：这就像微服务之间不共享 Java 对象、而用 HTTP+JSON 通信——各自可用不同语言/版本
构建，只要遵守接口契约。区别是这里是**同进程内**通过动态库函数指针调用，没有网络开销。

## 三、ABI 契约：6 个导出符号 + 1 张能力表

每个 Provider 动态库必须导出 6 个 C 符号（`provider_abi.h:75-87`）：

| 符号 | 作用 | 服务端类比 |
|---|---|---|
| `qp_provider_abi_version()` | 返回 `1u`，版本协商 | API 版本号 |
| `qp_provider_descriptor_json()` | 返回元信息 JSON | 服务发现/元数据端点 |
| `qp_provider_create(host, &handle)` | 建实例，接收 Host 能力表 | Bean 创建 + 依赖注入 |
| `qp_provider_request(handle, json, cb, userData)` | **异步**处理请求 | 主要 RPC 端点 |
| `qp_provider_cancel(handle, requestId)` | 按 id 取消未完成操作 | 请求取消 |
| `qp_provider_destroy(handle)` | 销毁实例 | Bean 销毁 |

**Host 能力表 `qp_host_api_v1`**（`provider_abi.h:46-57`）由 Host 在 create 时注入给 Provider，
相当于依赖注入。它提供 `log` 和 `secure_read/write/delete`——**Provider 因此不需要直接依赖
Keychain/DPAPI 等平台 API**，凭据存取反向委托给 Host。`struct_size` 字段允许未来在结构末尾
追加字段而兼容旧 Provider（向前兼容的经典手法）。

## 四、ProviderLoader：C ABI 与 Qt 世界的适配器

`ProviderLoader`（`provider_loader.hpp`）是 Host 侧的关键桥接组件，解决三个跨界问题：

1. **函数指针 ↔ C++ 成员函数**：C ABI 只能传函数指针，不能传成员函数。用**静态 thunk**
   （`responseThunk`/`logThunk`/`secure*Thunk`）先从 `void* userData` 找回 `this`，再转发到对象方法
   （`provider_loader.hpp:42-51`）。

2. **异步回包 ↔ Qt 信号**：Provider 完成后调用传入的 `qp_response_callback`，可能来自**网络线程**。
   `responseThunk → acceptResponse → emit responseReceived`，信号默认排队到 Qt 主线程事件循环，
   UI 因此总在主线程更新。

3. **陈旧回包过滤（generation 代号）**：`generation_` 每次 `load` 递增。用户在极短窗口内切换/卸载
   题库时，排队中的旧回包携带旧代号，`acceptResponse` 据此**丢弃属于已卸载题库的响应**，
   避免错误路由（`provider_loader.hpp:66-69`）。这是异步 + 可切换资源场景的通用防御，值得记住。

> 另一处克制的设计：`pendingRequests_` 只记录方法名、耗时、错误摘要，**不保存题目/答案等 RPC 参数**
> （`provider_loader.hpp:63`），既便于用户反馈排查，又不扩大日志内容范围。

## 五、DeclarativeProvider：内置声明式题库的 9 个方法

`DeclarativeProvider::request()`（`declarative_provider.cpp:528`）把 method 分发到 9 个
`handleXxx()` 处理方法（`switch` 分发，`declarative_provider.hpp:44-52`）：
`initialize` / `capabilities` / `catalog.list` / `attempt.create` / `attempt.questions` /
`attempt.saveAnswers` / `attempt.submit` / `attempt.report` / `attempt.solutions`。
它们如何驱动做题见 [01 用户做题逻辑](01-用户做题逻辑.md) 的泳道图。几处值得注意的实现：

- **`load()`**（`:81`）：`findManifest` 逐级上查 → 读 `bank.json` → 校验 manifest/bank 的
  `schemaVersion` 一致 → `validateBankDetailed`。任何不一致都 `fail`，不静默放行。
- **`expandSectionCatalogs()`**（`:145`）：兼容早期"单 catalog + `source.sectionId`"的多套题库，
  **仅在内存中**展开成"每套一个 catalog"，原 `bank.json` 无需迁移。`document` 参与分组键，
  避免两份文件都叫 `set-1` 被误合并；跨套共享材料时保持旧 catalog 不拆分。
- **`buildUnits()`**（`:250`）：普通题是单题单元，共享 `materialId` 的题目合并成**不可拆分的题组单元**，
  顺序取首次出现位置、不重排。组卷时题组永远整体加入，即使超出目标题量也不截断。
- **`practiceHistoryByQuestion()`**（`:365`）：一次遍历全量题目、逐题查一次 `QSettings`，
  把 `questionId -> "correct"/"wrong"` 载入内存表；`handleCatalogList()` 的掌握度统计和
  `handleAttemptCreate()` 的掌握题过滤共用同一份表，避免两处各自触发一遍高频注册表读取。
- **判分与历史**（`handleReport()`, `:502`）：`answers_ == expected` 比较 `QSet<int>`（天然支持多选），
  结果回写 `QSettings` 的 `practice/history/<providerId>/<questionId>`，供下次组卷做掌握度过滤。
- **`solutionsView()`**（`:380`）：`hostQuestions(true)` 的缓存，`handleReport()` 判分和
  `handleSolutions()` 展示共用；`handleAttemptCreate()` 换卷时通过 `solutionsCacheValid_` 失效。

## 六、重构建议

1. **【已完成，2026-09-06】`request()` 的长 `if` 链已改为 `switch` 分发表**。
   `methodForName` 映射出的 `enum Method` 现在经 `request()`（`:528-546`）里的
   `switch` 分发到 9 个 `handleXxx()` 方法（`declarative_provider.hpp:44-52`），
   每个方法体独立、可单测；原来嵌在同一个函数体内的 choice 解析、组卷逻辑随之拆开。

2. **【中】内置 Provider 与 C ABI 的关系可更显式**。`DeclarativeProvider` 是纯 C++ 类，
   由 `ProviderLoader` 在"未加载动态库"时直接调用（`provider_loader.hpp:55` 持有 `declarative_`）。
   建议在代码或文档里画清"内置走 C++ 直调、第三方走 C ABI"这条分叉，避免新人误以为内置也过 ABI。

3. **【已完成，2026-09-06】`attempt.report` 里 `hostQuestions(true)` 重复计算已消除**。
   新增 `solutionsView()`（`:380`）缓存"带答案"的题目视图，`handleReport()` 和
   `handleSolutions()` 共用同一份；`handleAttemptCreate()` 换卷时清空缓存。

## 七、性能建议

- **【已做，标杆】`catalog.list` 掌握度统计 O(题+类)**：原本"逐分类 × 全量题"会在大题库多分类时
  触发上万次 `QSettings::value()`（Win7 落注册表尤其卡），已改为一次遍历累计到内存表
  （`handleCatalogList()`，`declarative_provider.cpp:403-439`）。
- **【已做】`questionCountByCatalog_` 预算索引**：`load` 时算一次，`catalog.list` 查表
  （`declarative_provider.hpp:57`）。
- **【已完成，2026-09-06】`attempt.create` 的掌握题过滤复用一次性载入的历史表**：
  `handleAttemptCreate()`（`:441-478`）改为调用 `practiceHistoryByQuestion()`，与
  `handleCatalogList()` 共用同一份一次性遍历的 `questionId -> 状态` 表，
  不再各自触发一遍逐题 `QSettings::value()`。

## 八、可读性建议

- `provider_abi.h` 的注释是全项目"讲清为什么"的范例（C ABI 决策、`struct_size` 兼容、
  能力表注入）。新增 ABI 字段时保持同样密度的"为什么"注释。
- 第三方插件作者的**上手门槛**主要在"要导出哪 6 个符号、JSON 长什么样"。`providers/template/`
  已提炼出带注释的最小骨架（见 07 章节的执行进度，或直接看目录本身），新增第三方 provider
  可从这里复制起步，不必再从 `providers/demo` 里摘取。

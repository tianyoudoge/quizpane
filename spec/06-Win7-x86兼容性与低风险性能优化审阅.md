## 1. 结论

项目已有 Win7 x86 专门构建，普通刷题、JSON 题库、TXT/DOCX、文字 PDF 和网课伴侣均有对应实现路径，不能概括为“32 位大部分功能不支持”。但存在以下明确边界：

1. **内置更新不适合直接向 Win7 x86 承诺可用**：更新资产固定选择 x64；安装脚本还依赖 `Expand-Archive`。
2. **正式 Win7 发布流程默认关闭本地 OCR**：扫描 PDF 不能完整本地识别；实验 OCR 包与正式包要分开说明。
3. **原生 DLL 题库平台分派缺 x86**：当前 Windows 非 ARM 分支返回 `windows-x64`。普通声明式 JSON 题库不走此分派。
4. **大文档容量是主要限制**：已有整页 PNG 缓存和部分渲染保护，但并非全进程预算，不能保证 32 位不耗尽地址空间。
5. 网课 Windows 路径使用真实浏览器 popup，不依赖 Chrome 116 的实验捕获链路；课程网站是否还能在 Chrome 109 正常播放，需要逐站验证。

建议先修兼容缺陷，再按第 4 节处理低风险性能项；不要先降低识别精度、放宽校验或增加 OCR 并发。

### C1 · 更新资产固定 x64（P1，代码确认）

- 入口：`apps/desktop-qt/src/ui/main_window.cpp::updateAssetForCurrentPlatform()` → `checkForUpdates()` 所在更新检查流程 → `downloadAndInstallUpdate()` → `startDownloadedUpdate()`。
- Qt5/Win7 分支固定返回 `QuizPane-windows7-x64-portable.zip`，未判断编译架构。发布流程实际提供 x86 包，因此属于选择逻辑遗漏。
- 触发：x86 用户接受新版本更新。若服务返回该 x64 资产及摘要，校验通过仍会下载错误架构；如脚本成功覆盖，64 位 EXE 无法在 32 位系统运行。
- 后续规格：按**程序构建架构**选择资产，区分 x86/x64/ARM；未知组合拒绝自动安装。即使 x86 程序运行在 x64 系统，也应保持升级为 x86。
- 验收：Qt5 x86/x64、Qt6 支持组合分别断言资产名；缺资产时不退出、不覆盖；真实 Win7 x86 做一次完整升级并启动新程序。

### C2 · 自动更新依赖 PowerShell 解压能力（P1，代码与平台资料确认）

- `MainWindow::startDownloadedUpdate()` 只查找 `powershell.exe`，生成的脚本直接调用 `Expand-Archive`；没有检查该命令或模块是否存在。
- Win7 自带 PowerShell 2.0；`Expand-Archive` 是 PowerShell 5 时代提供的能力。因此默认旧环境不能完成该解压步骤；安装过相应新版环境的机器需另测。参考：[微软 Win7/PowerShell 2.0 资料](https://download.microsoft.com/download/d/2/b/d2b12f2f-0183-4954-9b68-b2a216b55149/msdn_magazine_0711.pdf)、[微软 PowerShell 5 压缩说明](https://devblogs.microsoft.com/scripting/working-with-compressed-files-in-powershell-5/)。
- 脚本异常会写日志并尝试恢复旧程序，但这不是更新成功，也不能消除 C1 的风险。
- 最低风险规格：在退出前探测必需命令；能力不足时保留旧程序，提供正确 x86 包的手工更新入口。若要实现无外部依赖的自动更新，应单独设计使用现有 ZIP 库的解压与失败恢复，不当作小性能改动。
- 验收：PowerShell 2.0/5.1、中文和空格路径、目标文件锁定、磁盘不足、升级中断；任何失败都不得把“已启动脚本”当作完成。

### C3 · 原生题库平台 key 缺 x86（P1，代码确认）

- `ProviderInstaller::currentPlatformKey()` 在 Windows 非 ARM64 时总返回 `windows-x64`；`inspect()` 用此 key 选择 `runtime.libraries`，已安装题库发现也使用该 key。
- 正确标为 `windows-x86` 的 DLL 包不能按预期选中；含 x64 库的包可能被选中但无法由 x86 进程加载。不能据此断言所有历史自定义包都失败，因为历史包可能使用过错误标记。
- 后续规格：新增明确 x86 key，并核对 SDK 打包工具、manifest 示例、加载和已安装发现流程；不要把任意 x64 库回退当作 x86 加载。
- 验收：x86-only、x64-only、双架构、旧包、JSON 包；不支持架构应在导入时解释清楚，JSON 包行为保持一致。

### C4 · Win7 实机覆盖缺口

`release.yml` 与 `windows7-desktop.yml` 的宿主都是 `windows-2022`；打包检查、DLL 加载和 smoke 配置存在，但本次未查询这些工作流的实际运行结果。现代 Windows 上能加载，不证明依赖 DLL 的导入 API、旧 CPU、Win7 根证书和 PowerShell 都可用。最终需检查 EXE/DLL 的 PE 架构及导入，并在 Win7 SP1 x86 上验收。

当前构建已随包部署 VC142 CRT、UCRT、Qt5Pdf 和 OpenSSL，不能再把“没带这些运行库”列成已确认缺陷；实际发布 ZIP 内容本次未检验。

## 3. 性能与容量瓶颈

### P1 · 32 位内存保护不完整（优先级 P1，静态确认）

证据：`document_extractor.cpp::pdfRenderWouldExhaustCommit()` 的进程阈值是 `max(1.5 GiB, 物理内存×75%)`；没有基于进程位数设置上限，也未检查剩余用户态虚拟地址空间。该检查只由 `PdfRenderSession::renderPage()` 调用。

- 常规 32 位 Windows 用户态地址空间默认约 2 GiB，且连续分配可因碎片更早失败；增加分页文件不能突破这个边界。[微软虚拟地址空间说明](https://learn.microsoft.com/en-us/windows/win32/memory/virtual-address-space)
- 例如公式在报告物理内存为 3 GiB 时允许 Private Usage 达到 2.25 GiB 才因该项阻止渲染，不能保护默认 2 GiB 用户空间。Private Usage 也不等于已占用虚拟地址空间。
- 同时固定保留至少 2 GiB 系统提交额度，在小内存/小分页文件机器上可能过早停止辅助渲染。两个问题可同时存在。
- 扫描路径 `PdfExtractor::extract()` 直接调 `renderPdfPage()`；复核 `renderPdfReviewPage()` 直接调 `document.render()`，均没有这层检查。
- 单个 5000×5000 RGB32 图约 95.4 MiB；渲染、铺白、格式转换、裁切及 PNG 字节可叠加。200 MiB 整页 PNG 缓存并未覆盖这些临时内存，也不覆盖正式附件、复核图和所有文档总和。
- `PdfPageImageCache` 是每个缓存对象的预算，保留最后一项的实现还允许单项超过预算；不是全进程硬上限。批量工作流保留多个文档后，总量不能按单个缓存估算。

优化规格：统一各渲染入口的分配前检查，按 x86 设保守预算并结合可用虚拟空间/预计像素字节；阈值通过实机数据确定。扫描识别被阻止时必须明确报失败或逐页警告，不能变成空白页；辅助裁图被阻止保留文字及复核提示。不要把提高阈值或启用 `/3GB` 当作默认修复。

### P2 · 复核切题重复打开 PDF，已看图片持续累积（优先级 P1）

证据：`StudioWindow::ensureReviewAssetBytes()` → `renderPdfReviewPage()`。每个未缓存题目的每个 segment 都新建 `QPdfDocument` 并加载源文件，同页相邻题也重复渲染；在 UI 调用链中同步完成。生成的 PNG 插入 `reviewAssets_`，此处没有容量淘汰。

已做的懒加载降低了首次进入复核成本，但用户逐题浏览后缓存仍会累积。建议同一 UI 线程持有有限 PDF 会话及小容量整页缓存，优先命中相邻题；懒生成的复核 PNG 使用独立有界缓存。不能直接复用工作线程的 `QPdfDocument`，不能淘汰唯一的人工修图或正式附件。

### P3 · 云结果下载与适配仍整包进内存（优先级 P1）

证据：`MineruExtractionJob::download()` 在 `finished` 中 `readAll()`，然后才检查 512 MiB 上限并写盘。上限不是接收过程内存上限，超大响应在拒绝前已积累。`mineru_output_adapter.cpp` 的 ZIP 读取随后再次 `readAll()`，通过 `mz_zip_reader_init_mem` 打开，只选用所需 layout JSON。

两个阶段通常先后执行，不应直接宣称二者必然同时各占 512 MiB；但各阶段都有明显的大块内存和额外解析分配风险。

建议拆两步：下载 `readyRead` 分块写临时文件并累计限额，完成后提交；适配器使用支持中文路径的 QFile 随机读取回调打开 ZIP，保留条目安全、解压总量、layout 64 MiB 等检查。第二步改动面较大，风险高于单纯下载流式化。

### P4 · 复核树全量遍历与同步导出（优先级 P2）

- `populateReview()` 在 UI 线程逐项建树、展开和筛选，未用更新暂停包裹批量装载。可先减少布局/重绘，不应未经证据声称它存在逐行触发全树遍历的 O(N²) 问题。
- `refreshReviewDecisionState()` 每次确认/排除遍历全树，再筛选；`advanceToNextReviewIssue()` 从头寻找待处理题。连续处理大量题时累计成本明显，实际耗时待测。
- `packageProvider()` 同步序列化、压缩、自检、运行时重读校验及安装，可能阻塞 UI；多次读取里有防篡改和最终包自检目的，不能简单删除。

首轮只批量暂停树更新、合并一次用户操作的重复刷新并保留最终刷新。增量索引、模型视图替换、后台导出涉及状态一致性和生命周期，另行评估。

### P5 · OCR 每页初始化（优先级 P2，仅 OCR 包）

`recognizePage()` 每页构造 `TessBaseAPI`、`Init(chi_sim+eng)`、识别、`End()`；长扫描卷重复加载模型。可按文档复用单个线程内引擎，但自适应学习与页面状态可能改变结果，需明确清理策略及逐页回归。**不列为首批低风险项**，正式无 OCR 包也得不到这项收益。

### P6 · 结果导出预先持有所有图片（优先级 P2）

`MainWindow::exportAttemptResults()` 已按最多 72 行分图、无答案五题合并，避免无限长单图；但所有图仍存入 `QList<QImage> resultImages`。大练习可改为当前页按需生成和小缓存，保留导出内容、分页与字体布局；普通小练习不一定有可感收益。

## 4. 建议的低风险优化规格与排序

下列风险是相对现有语义的改动风险，不代表无需回归。没有基准数据，不预估提速百分比。

| 顺序 | 项目 | 风险/收益边界 | 验收与回退条件 |
|---|---|---|---|
| 1 | 复核树批量暂停更新，结束统一刷新 | 低；减少界面重绘，不改识别结果 | 100/1000/5000 题进入复核计时；父子勾选、hard 默认排除、筛选和计数一致。异常退出必须恢复 updatesEnabled；若无收益不扩成重构 |
| 2 | 缓存 UI 当前 PDF 会话与最近整页 | 低至中；同页连续切题收益明确，缓存必须很小且按字节限制 | 相邻 20 题记录 load/render 次数；跨文件、同名不同路径、源文件变化/删除、退出释放通过；坐标和裁图像素一致。失效即重载 |
| 3 | 懒生成复核 PNG 有界缓存 | 低至中；限制长时间复核内存增长 | 只淘汰可重建的 lazyReview 数据；遍历 500 题后内存趋于稳定，回访可重建，手工修图和最终包不丢失。预算值实测后定 |
| 4 | MinerU 流式下载与途中限额 | 低至中；显著减少大 ZIP 下载时内存需求 | 分块/无 Content-Length/空包/超限/断网/取消/写盘失败；成功文件与原字节一致，失败不留下可被恢复流程误认的完整 ZIP；重试仍回 poll 获取新签名 URL |
| 5 | x86 内存预算与渲染保护覆盖 | 中；优先稳定性，会改变触发降级的时机 | 扫描失败不伪装空白，辅助图缺失有复核提示；2/4 GiB 配置、小分页文件、大页尺寸、连续复核；不靠自动降 DPI 改变识别质量 |
| 6 | 结果导出按页生成、小缓存 | 低至中；仅大练习有明显价值 | 同输入各页图片一致，前后翻页和保存正确；峰值随缓存页数而非总结果页数增长 |

第二批再评估：MinerU ZIP 随机读取、OCR 引擎复用、复核索引、后台打包。正式包中不存在的 OCR 开销不要作为全体用户优化收益。

保留已有优化：文字 PDF 按需渲染、1.5x 提取渲染、低压缩中间 PNG、整页缓存、分套共享 `PdfRenderSession`、普通校对图懒加载、生成工作线程、云端退避轮询、结果图片分页。以上不重复列成“尚未实现”。

不建议首轮做：降低 OCR/裁图分辨率、换模型、修改答案识别规则、放宽 ZIP 限额、删除最终校验、并行多个 PDF/OCR 大任务。这些更易影响识别结果、正确性或 x86 峰值内存。

## 5. 容易误判为 Win7 问题的通用限制

- `ProviderInstaller` 当前最多 256 个 ZIP 条目、解压总量最多 128 MiB；图多的题库在其他系统也可能自检失败。两个基本 JSON 文件之外的资源预算还要计入目录等条目，不能直接承诺“支持 256 张图”。
- `packageProvider()` 遍历整个 `generatedAssets_` 打包；排除题目后是否保留无引用附件值得专项检查。若做裁剪必须完整遍历材料/题干/选项引用，避免把它归类为无需验证的删除优化。
- 制作器的复核编辑没有磁盘草稿；x86 内存崩溃可能丢失未导出的人工编辑。这与主程序答题草稿不是同一功能。
- 题号、题型、材料正文等编辑限制，以及跨域 iframe/非标准网页播放器控制限制，是当前产品边界，不是 Win7 专属缺失。参见 [05](05-识别后手工编辑与导出.md) 和扩展 README。

## 6. 后续验收计划

### 6.1 兼容性

使用 Win7 SP1 x86 虚拟机或实机，分别测默认 PowerShell 2.0 与具备 5.1 的配置；2 GiB/4 GiB 内存、不同分页文件配置。包从全新中文/空格目录解压，不借用开发机 PATH、Qt、OpenSSL 或 OCR 模型。

必须覆盖：两个 EXE 启动；TXT/GB18030/DOCX/文字 PDF/混合 PDF/扫描 PDF；正式无 OCR 包与实验 OCR 包区分；含/无答案和多选完整链路；云端鉴权、TLS 与断点恢复；JSON 和原生题库；x86 更新失败保护；Chrome 109 绑定、置顶、老板键和恢复；结果图导出。

### 6.2 性能

样本分开测：纯文字卷、图表卷、扫描卷、多文件合订批次；20/100/300 页；100/1000/5000 题；小/中/接近限额的云结果 ZIP。超出当前业务限制的样本用于失败处理，不要求成功导入。

同一 Release 包配置、输入和机器测基线/改动后，冷启动与热缓存分开，各至少三轮；记录中位数、尾部延迟、Private Bytes 峰值、虚拟地址占用、系统提交余量、缓存字节数、PDF 打开/渲染次数。阶段分别记录提取、规则、首次复核、连续切题、导出，避免只看总耗时。

正确性验收：题目数、顺序、答案、来源坐标、warnings、复核等级、正式附件及解码后图片像素一致；有意的内存降级单独验证。ZIP 时间戳可能变化，应比较展开内容而非要求整包 SHA 一致。

复用相关现有测试：`document_extractor_test`、`mineru_client_test`、`mineru_output_adapter_test`、`rule_based_generator_test`、`declarative_provider_flow_test`、`result_image_preview_test`。这些不替代 Win7 x86 实机验收；未来改动只跑对应范围后再进行目标机验证。
